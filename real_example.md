In the Prompt-to-VR platform, imagine a user submits a detailed prompt that says: "I want a Quest 3 Iron Man VR game set in New York City where users don't fly but can run around the city with Iron Man's repulsor gauntlets and can shoot anything just for fun." For this example VR Game we only mention one scene, two assets, and six mechanics, though a full game would have many more of each. The pipeline turns that prompt into structured artifacts in a fixed order: BuildSpec → AssetManifest → MechanicPlan → SceneSpec → reference images → Tripo image-to-3D → asset normalization → generated C++ → scene compile → CMake build → launch.

In the BuildSpec stage the game is scoped at a high level: the scenes the user will play through (here just one — the New York environment), the mechanics the game will need (locomotion, snap turn, grab, equip, shooting hub, repulsor blast), the high-level asset needs called out by the prompt (the Iron Man gauntlet prop and the New York City environment), and the acceptance goals the final build must satisfy before it is considered playable. This stage does not yet decide whether a mechanic is reusable or needs to be coded from scratch — it just captures the game's intent in a strict, schema-validated form so every downstream stage reads structured data instead of the raw prompt.

In the AssetManifest stage the high-level asset needs from the BuildSpec are turned into a concrete list of `AssetItem` entries, each with a category (`environment`, `prop`, `character`, `fx`, or `ui`), style notes, and generation hints that the later stages will consume. For this Iron Man game the AssetManifest emits two entries: one `environment` item for "Manhattan city block, daytime, photoreal" and one `prop` item for the "Iron Man gauntlet, MK-style, gold-and-red PBR, paired left/right". Later, after the SceneSpec has been composed and every asset has a confirmed role in the scene, reference images for each `AssetItem` are generated with Gemini / Imagen (a few candidates per asset), and the chosen images are sent to Tripo's image-to-3D API with textured PBR output (`texture=True`, `pbr=True`, `texture_alignment="original_image"`). The result is a GLB for each gauntlet and a GLB for the New York environment, stored under `projects/<id>/assets/<asset_id>/model.glb`.

Next the MechanicPlan stage classifies every mechanic the game needs into one of three buckets: fully prebuilt into the engine and usable as-is (`builtin`), prebuilt but needing per-game tuning (`builtin+config`), or requiring fully custom C++ to be generated for this game (`generate`). The planner is given the full live engine catalog (every built-in mechanic plus every mechanic the engine has previously promoted from past games into `engine/promoted/registry.json`)  For this Iron Man game the planner classifies the six mechanics as 3 builtin, 1 builtin+config, and 2 generate. The placement of each mechanic into one of these buckets depends on a combination of what the engine already has prebuilt and what the user's prompt is actually asking for. 

* Builtin Mechanics  
  * Locomotion — Because this Iron Man game does not include flight, the player uses the engine's built-in smooth locomotion as-is: the left joystick moves the VR character forward, back, left, and right relative to the head direction. No tuning is needed, so the planner just declares "this game uses `builtin.smooth_locomotion`" and moves on.  
  * Snap Turn — The right joystick (the joystick not used for forward / back / left / right locomotion) is used for snap turning. Pushing it left or right rotates the VR character 45° in that direction. The engine's snap turn module covers this out of the box, so this is also declared as `builtin.snap_turn`.  
  * Grab — The engine's grab system already handles Quest grip-squeeze to pick up, hold, release, and throw any prop that participates in the grab system. This mechanic is labeled `builtin` (not `builtin+config`) for this project because making the imported gauntlet grabbable is not done by rewriting grab or generating a second grab system. Instead, the mechanic planner declares that this game uses the built-in grab mechanic, and later in the SceneSpec stage each gauntlet is wired as an entity into that system: the entity references the gauntlet GLB and carries the tag `grabbable` *and (optionally) includes a `builtin.grab` mechanic binding as a declarative ‘this entity participates in grab’ hook (it currently just adds a `CGrabbable` marker component), while the actual ability to pick it up comes from the `grabbable` tag and the engine’s grab loop* The engine's already-running Grab mechanic walks the world every frame, sees those bindings, and immediately knows the gauntlets are valid grab targets — no custom code, no per-game grab fork.  
* Builtin \+ Config Mechanics  
* Equip — The engine's Equip mechanic lets any tagged object be equipped to any part of the VR character's body by default. The `+config` part means the planner can set per-object parameters that tune Equip for this specific game. Crucially, every Equip parameter is independently optional — the planner can use any one of them on its own, can combine them, or can omit all of them and accept the default "this object equips anywhere on the body" behavior. The three parameters Equip understands are:  
  * Allowed body part(s) (optional). A short allowlist of named body slots the object may attach to, drawn from the engine's skeleton vocabulary (e.g. `head`, `chest`, `waist`, `back`, `left_hand`, `right_hand`, `left_forearm`, `right_forearm`, `left_foot`, `right_foot`). If set, the object can only land on the listed slots and is rejected anywhere else. Examples: a helmet sets `["head"]`, a one-handed sword sets `["left_hand", "right_hand"]`, a backpack sets `["back"]`. If omitted, the object is not restricted by slot — narrowing comes from parameter 2 or 3 if either of those is set, or stays fully open if neither is.  
  * Custom equipable range (optional). A pair of anchor points on the avatar skeleton that define the start and stop of the object's coverage along a limb or body region — for example `start = "left_elbow"`, `end = "left_fingertips"`, or `start = "head_top"`, `end = "waist"`. Because the anchor names themselves identify which limb and which side they live on, the engine can infer the relevant body part from this parameter alone — the planner is not required to also fill in parameter 1\. If only this parameter is set, the object is restricted to the limb / region implied by its two anchors and rejected everywhere else. If omitted, the object covers the engine's default coverage area for whichever slot it lands in.  
  * Equip offset, rotation, and attachment behavior (optional). Three sub-fields that fine-tune how the object snaps into place once a valid slot is found: a positional offset relative to the anchor frame (e.g. shift the object 2 cm outward from the forearm so it doesn't clip the skin), a rotation offset (e.g. roll a sword grip 15° so the blade points forward instead of straight up), and an attachment mode (`rigid_weld` to follow the limb 1:1, `soft_follow` for a slight lag, or `snap_only` to sit on the slot without inheriting limb motion). If omitted, the engine uses sensible defaults — anchor-aligned, no offset, rigid weld.  
* Because the three parameters are independent, the planner only uses the ones that actually matter for a given prop. A simple helmet uses only parameter 1 (`["head"]`). A simple one-handed sword uses only parameter 1 (`["left_hand", "right_hand"]`). A full-body chest harness might use only parameter 2 (`start = "head_top"`, `end = "waist"`). An oddly oriented weapon hilt might use parameter 1 plus a parameter 3 rotation offset. For our Iron Man gauntlets the planner only needs parameter 2 — `start = "left_elbow"`, `end = "left_fingertips"` on the left gauntlet and `start = "right_elbow"`, `end = "right_fingertips"` on the right. Because the anchor names are sided, the engine infers that the slot is the left or right forearm respectively, automatically rejects landing on the head / chest / legs, and automatically pairs the left gauntlet with the left arm and the right gauntlet with the right — all without the planner having to also fill in parameters 1 or 3\. The configuration travels as parameters on the SceneSpec binding, not as a new C++ file, because the prebuilt Equip mechanic already understands all three parameters.  
* Generate Mechanics  
  * Shooting-Hub — The shooting-hub is a hub mechanic that listens for trigger pulls whenever the player is holding or has equipped an object tagged as a weapon. It is meant as a core hub that every shooting-style mechanic in this game (and in future games) can be built off of. The hub does not define every weapon's look and feel; it routes trigger input to a *weapon profile* — game-specific firing logic (repulsor vs. pistol vs. rocket vs. bow) is separate generated code that registers a `weapon_profile_id` against the hub and implements its own projectile, VFX, and timing. Because the engine does not already ship a shooting-hub that listens for the correct trigger while the player is holding or wearing a weapon-tagged object (right trigger for the right hand, left trigger for the left), the planner classifies this `generate`. Once it has been written and successfully compiled, the engine's promotion stage will index it into `engine/promoted/registry.json`, so future games (a sci-fi shooter, a fantasy bow-and-arrow game, a John Wick game) can reuse the same hub without regenerating it.  
  * Repulsor Blast — The repulsor blast fires a beam-style Iron Man projectile out of whichever gauntlet the player has equipped, when they press the trigger on that same side. Pressing the right trigger with only the left gauntlet equipped does nothing, and pressing the left trigger with only the right gauntlet equipped does nothing. This mechanic explicitly depends on the Shooting-Hub being created first, because it builds *on top of* the hub — it does not re-implement grab, equip, or trigger listening, since Shooting-Hub already sits on top of Grab and Equip. The Repulsor Blast's generated code therefore needs to:  
    * A. Register a `weapon_profile_id` of `iron_man_repulsor` against the Shooting-Hub, so the hub knows to call into this code whenever a gauntlet with that profile receives a trigger press.  
    * B. Match the trigger side against the gauntlet's equipped side, so the left-gauntlet profile only fires on left-trigger pulls and the right-gauntlet profile only fires on right-trigger pulls.  
    * C. Implement the actual visual and gameplay behavior of the blast — the beam's spawn point at the palm of the gauntlet, the beam's direction aligned to the gauntlet mesh's forward axis, the canonical gold/blue-white VFX, any charge or cooldown timing, and whatever the blast does on impact.  
* It places one entity per `AssetItem` from the AssetManifest, each pointing at the right GLB and tagged in a way the rest of the engine can react to. For this game the composer emits:  
  * A `manhattan_city` entity at position `[0, 0, 0]` with rotation identity, `physics.kind = "static"`, `physics.collision_shape = "mesh"` (so the player can actually walk on the sidewalks and collide with buildings), and tags `["environment"]`. The player spawn sits on top of this entity.  
  * A `gauntlet_left` entity within arm's reach of the spawn (e.g. \~0.6 m in front of and slightly to the left of the player, at hand height), referencing the gauntlet GLB, with `physics.kind = "dynamic"`, an AABB or sphere collision shape, and tags `["interactable", "grabbable", "wearable", "weapon", "hand_left"]`.  
  * A `gauntlet_right` entity symmetric to the left, tagged `["interactable", "grabbable", "wearable", "weapon", "hand_right"]`.  
* It wires every mechanic from the MechanicPlan onto the right entities via `MechanicBinding` entries. This is the moment the planner's abstract classifications become concrete runtime wiring:  
  * The player rig gets a `builtin.smooth_locomotion` binding and a `builtin.snap_turn` binding (no params beyond defaults — the engine handles joystick polling internally).  
  * Each gauntlet entity gets a `builtin.grab` binding, so the engine's Grab mechanic recognizes them and makes them grabbable on a grip-squeeze.  
  * Each gauntlet entity gets a `builtin.equip` binding carrying the exact parameters the MechanicPlan tuned for this game: `{ "slot": "forearm_left"` or `"forearm_right", "coverage_start": "fingertips", "coverage_end": "elbow", "pair_with": "gauntlet_right"` (or `"gauntlet_left"`) `}`. This is exactly the per-game tuning that made Equip a `builtin+config` instead of a plain `builtin` — the configuration travels as parameters on the binding, not as a new C++ file.  
  * Each gauntlet entity also gets a `generated.shooting_hub` binding declaring it carries a weapon profile, plus a `generated.repulsor_blast` binding with params like `{ "side": "left"` or `"right", "weapon_profile_id": "iron_man_repulsor", "muzzle_anchor": "palm", "forward_axis": "z+" }`.  
* It places the lights and sky for the scene. For daytime Manhattan that means one directional "sun" light angled across the block, a daylight sky color, and a moderate ambient intensity so the gauntlet's PBR materials read correctly under the sun-plus-shadow lighting.

In short, the SceneSpec is the bridge between the abstract MechanicPlan and the deterministic runtime. It turns sentences like "the gauntlet should be grabbable, equippable on the forearm, and fire repulsors on trigger" into concrete entity ids, transforms, mesh refs, tags, and mechanic bindings that the engine's scene loader can apply directly to the ECS world — and that the C++ code-generation stage can target by name. 

In the Code Generation stage the orchestrator turns each `generate` entry in the MechanicPlan into a `CodeTask` and enrolls it into a per-project ledger at `projects/<project_id>/codegen_board.json` (the “codegen board”). For our Iron Man game this means two tasks are written to the board: `shooting_hub` and `repulsor_blast`. The board records each task’s name, summary, the `ptv::IMechanic` interface it must implement, its `depends_on` list, linked assets (the gauntlet GLBs), the target scene (New York), and an initial status. Because Repulsor Blast declares `depends_on: ["shooting_hub"]`, `shooting_hub` starts as `pending` and `repulsor_blast` starts as `blocked`. There is no static “Shooting-Hub goes first, Repulsor goes second” schedule — the board enforces order through state alone.

The orchestrator then spins up a thread pool of up to `codegen_max_parallel_agents` workers (default `3`). Workers are not pre-assigned to tasks. Every worker runs the same loop and uses only the OpenAI / ChatGPT path (or OpenAI Agents SDK) for this stage:

1. `board.refresh_blocked()` — promote any `blocked` task whose deps are all `done` to `pending`.  
2. `task = board.atomic_claim_next_pending(agent_id)` — atomically claim the next `pending` task in FCFS order (a file lock under `projects/<project_id>/` keeps two workers from grabbing the same row).  
3. If no task is returned, the worker exits cleanly.  
4. Run the codegen LLM flow for the claimed task.  
5. `board.mark_done(task_id, files_written)` (or `mark_failed`) with the resulting `.cpp` path and `.codetask.json` sidecar.  
6. Loop.

For our Iron Man build, on the first pass `shooting_hub` is the only `pending` task. The first worker to reach the claim step becomes the Shooting-Hub worker by virtue of winning the atomic claim; the board flips that task to `in_progress` and stamps it with that worker’s `agent_id`. Any other workers that race in find `shooting_hub` already claimed and `repulsor_blast` still `blocked`, so they get `None` and either retry or exit — they do not dead-spin on a specific dependency.

The Shooting-Hub worker then follows a disciplined flow:

* A. It reads the task metadata — name, summary, the `ptv::IMechanic` interface it must implement, its `depends_on` list (empty), the assets it is linked to (empty), and its target scene (New York).  
* B. It reads the ledger’s completed entries. Shooting-Hub has no upstream codegen tasks; its conceptual prerequisites (Grab, Equip) live in the engine’s public surface under `engine/runtime/include/ptv/api/`, so there is nothing to wait on.  
* C. It may use the web search tool to research the best way to design a generic shooting hub for VR — so the hub is a clean central abstraction that every shooting-style mechanic (pistols, rifles, RPGs, laser blasters, repulsors, bow-and-arrow, etc.) can plug into without each weapon re-implementing input handling.  
* D. It writes `engine/generated/mechanics/<project_id>/shooting_hub.cpp` (path-checked by `assert_path_allowed`, content cleaned by `filter_cpp_only` / `repair_generated_cpp`). The file implements `ptv::IMechanic`, registers itself with `PTV_REGISTER_MECHANIC("shooting_hub", ShootingHub)`, listens for the correct trigger (left or right) only when the bound entity has the `weapon` tag and is currently being held or worn, and forwards the trigger event to whatever generated mechanic has registered a `weapon_profile_id` against the same entity.

When that worker calls `mark_done("shooting_hub", files_written=[...])`, the board flips Shooting-Hub from `in_progress` to `done` and records its written file list and `.codetask.json` sidecar. An SSE event is emitted (`task_completed`). On the next loop iteration, any free worker that calls `refresh_blocked()` will see that every entry in `repulsor_blast.depends_on` is now `done` and will promote `repulsor_blast` from `blocked` to `pending`. The first worker to reach the atomic claim wins it — that may be the same worker that just finished Shooting-Hub, or a different one that was idle. There is no notion of a dedicated “Repulsor worker” reserved up front.

Whichever worker wins the claim then runs the same disciplined flow for Repulsor Blast:

* A. It reads the task metadata — name, summary, the `ptv::IMechanic` interface, its `depends_on` list (`["shooting_hub"]`), its linked assets (the left and right gauntlet GLBs), and its target scene (New York).  
* B. It reads the ledger and pulls the completed Shooting-Hub entry — its file path, exported registration symbols, the `weapon_profile_id` registration API, and the trigger callback signature — so the Repulsor Blast plugs into the real hub surface rather than reimplementing grip or attach. Because Shooting-Hub is already `done` on the board, this load is just a read; no waiting, no polling.  
* C. It may use the web search tool to research Iron Man, what a repulsor blast is and looks like, how the blast is fired from the palm of the gauntlet, VR projectile patterns, and gauntlet-aligned VFX (color, glow, trail, impact sparks).  
* D. It writes `engine/generated/mechanics/<project_id>/repulsor_blast.cpp` (again gated by `assert_path_allowed` / `filter_cpp_only` / `repair_generated_cpp`). The file implements `ptv::IMechanic`, registers an `iron_man_repulsor` weapon profile against the Shooting-Hub, matches the trigger side to the gauntlet’s equipped side (left trigger fires only when the left gauntlet is equipped, right trigger fires only when the right is), spawns a beam or fast projectile from the palm anchor of the gauntlet mesh oriented along the gauntlet’s forward axis, applies the canonical gold/blue-white color and motion of the repulsor, and respects any cooldown or charge timing the design called for. When done it calls `mark_done("repulsor_blast", files_written=[...])`, the board flips the row to `done`, and another SSE event fires.

Throughout the stage the board is the single source of truth: workers never message each other directly, dependency order is encoded purely in `depends_on` \+ state transitions, FCFS atomic claim prevents duplicate work, and observability comes from SSE events at `board_init`, `task_claimed`, `task_unblocked`, and `task_completed` / `task_failed`. The stage record’s message summarizes counts of `done` / `failed` / `blocked` so the UI can show progress. Existing safety nets — `.codetask.json` sidecars, generated-bounds checks, and the per-project lock — keep codegen and the downstream CMake build from racing each other.

The same pattern scales to any future game: one Shooting-Hub task, many parallel weapon-profile tasks (guns, repulsors, bows, magic wands, energy waves), all coordinated through the same board with `depends_on: ["shooting_hub"]`, without ever regenerating locomotion, snap turn, grab, or equip for each new prop. And once this build succeeds, the engine’s promotion stage indexes `shooting_hub` and `repulsor_blast` into `engine/promoted/registry.json`. The next prompt — say, “I want a Captain America VR game where his shield is grabbable, throwable, and fires energy waves” — will see those mechanics in the catalog as `promoted.shooting_hub` and `promoted.repulsor_blast`. The planner will be able to mark Shooting-Hub as `builtin` for that game and only emit a `generate` task for the new energy-wave weapon profile, which then enters a fresh board with `depends_on: ["promoted.shooting_hub"]` already satisfied — making it `pending` from the moment the board is initialized. That is the engine-growth loop: every game built on the platform turns yesterday’s `generate` work into today’s already-`done` dependency, making the next game cheaper, more reliable, and faster to plan.

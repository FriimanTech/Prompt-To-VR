In the Prompt-to-VR platform, imagine a user submits a detailed prompt that says: "I want a Quest 3 Iron Man VR game set in New York City where users don't fly but can run around the city with Iron Man's repulsor gauntlets and can shoot anything just for fun." For this example VR Game we only mention one scene, two assets, and six mechanics, though a full game would have many more of each. The pipeline turns that prompt into structured artifacts in a fixed order: BuildSpec → AssetManifest → MechanicPlan → SceneSpec → reference images → Tripo image-to-3D → asset normalization → generated C++ → scene compile → CMake build → launch.

In the **BuildSpec** stage the game is scoped at a high level: the scenes the user will play through (here just one — the New York environment), the mechanics the game will need (locomotion, snap turn, grab, equip, shooting hub, repulsor blast), the high-level asset needs called out by the prompt (the Iron Man gauntlet prop and the New York City environment), and the acceptance goals the final build must satisfy before it is considered playable. This stage does not yet decide whether a mechanic is reusable or needs to be coded from scratch — it just captures the game's intent in a strict, schema-validated form so every downstream stage reads structured data instead of the raw prompt.

In the **AssetManifest** stage the high-level asset needs from the BuildSpec are turned into a concrete list of `AssetItem` entries, each with a category (`environment`, `prop`, `character`, `fx`, or `ui`), style notes, and generation hints that the later stages will consume. For this Iron Man game the AssetManifest emits two entries: one `environment` item for "Manhattan city block, daytime, photoreal" and one `prop` item for the "Iron Man gauntlet, MK-style, gold-and-red PBR, paired left/right". Later, after the SceneSpec has been composed and every asset has a confirmed role in the scene, reference images for each `AssetItem` are generated with Gemini / Imagen (a few candidates per asset), and the chosen images are sent to Tripo's image-to-3D API with textured PBR output (`texture=True`, `pbr=True`, `texture_alignment="original_image"`). The result is a GLB for each gauntlet and a GLB for the New York environment, stored under `projects/<id>/assets/<asset_id>/model.glb`.

Next the **MechanicPlan** stage classifies every mechanic the game needs into one of three buckets: fully prebuilt into the engine and usable as-is (`builtin`), prebuilt but needing per-game tuning (`builtin+config`), or requiring fully custom C++ to be generated for this game (`generate`). The planner is given the full live engine catalog (every built-in mechanic plus every mechanic the engine has previously promoted from past games into `engine/promoted/registry.json`) and is instructed to prefer reuse over regeneration in that exact order — try `builtin` first, then `builtin+config`, and only emit `generate` when no catalog entry reasonably fits. For this Iron Man game the planner classifies the six mechanics as **3 builtin, 1 builtin+config, and 2 generate**. The placement of each mechanic into one of these buckets depends on a combination of what the engine already has prebuilt and what the user's prompt is actually asking for.

* **Builtin Mechanics**

  * **Locomotion** — Because this Iron Man game does not include flight, the player uses the engine's built-in smooth locomotion as-is: the left joystick moves the VR character forward, back, left, and right relative to the head direction. No tuning is needed, so the planner just declares "this game uses `builtin.smooth_locomotion`" and moves on.

  * **Snap Turn** — The right joystick (the joystick not used for forward / back / left / right locomotion) is used for snap turning. Pushing it left or right rotates the VR character 45° in that direction. The engine's snap turn module covers this out of the box, so this is also declared as `builtin.snap_turn`.

  * **Grab** — The engine's grab system already handles Quest grip-squeeze to pick up, hold, release, and throw any prop that participates in the grab system. This mechanic is labeled `builtin` (not `builtin+config`) for this project because making the imported gauntlet grabbable is **not** done by rewriting grab or generating a second grab system. Instead, the mechanic planner declares that this game uses the built-in grab mechanic, and later in the SceneSpec stage each gauntlet is wired as an entity into that system: the entity references the gauntlet GLB and carries the tag `grabbable` plus a `MechanicBinding` to `builtin.grab`. The engine's already-running Grab mechanic walks the world every frame, sees those bindings, and immediately knows the gauntlets are valid grab targets — no custom code, no per-game grab fork.

* **Builtin + Config Mechanics**

  * **Equip** — The engine's Equip mechanic lets any tagged object be equipped to any part of the VR character's body by default. The `+config` part means the planner sets per-object parameters that tune Equip for this specific game. There are two parameters relevant here:
    1. **Which body part(s) the object may attach to.** For a generic glove the planner might restrict it to the hand slot. For our Iron Man gauntlets the planner restricts attachment to the forearm slot only — meaning the gauntlets cannot be equipped to the head, chest, legs, etc.
    2. **A custom equipable range along that body part**, expressed in the prebuilt Equip mechanic's own parameter language as a start and stop point along the limb. For the Iron Man gauntlets that range runs from the fingertips up to the elbow, just like the comics and films. Configuring this parameter on the gauntlet prop means the gauntlet snaps only onto the forearm slot, and only covers the fingertip-to-elbow region of the avatar's arm — anywhere else is rejected.

    Left-vs-right pairing is also handled here: each gauntlet declares which forearm slot it belongs to so the engine never lets the left gauntlet snap onto the right forearm, and vice versa. Note that all of this is *parameters on the binding* — there is no generated C++ for Equip in this game, because the prebuilt Equip mechanic already understands those parameters.

* **Generate Mechanics**

  * **Shooting-Hub** — The shooting-hub is a hub mechanic that listens for trigger pulls whenever the player is holding or has equipped an object tagged as a weapon. It is meant as a core hub that every shooting-style mechanic in this game (and in future games) can be built off of. The hub does **not** define every weapon's look and feel; it routes trigger input to a *weapon profile* — game-specific firing logic (repulsor vs. pistol vs. rocket vs. bow) is separate generated code that registers a `weapon_profile_id` against the hub and implements its own projectile, VFX, and timing. Because the engine does not already ship a shooting-hub that listens for the correct trigger while the player is holding or wearing a weapon-tagged object (right trigger for the right hand, left trigger for the left), the planner classifies this `generate`. Once it has been written and successfully compiled, the engine's promotion stage will index it into `engine/promoted/registry.json`, so future games (a sci-fi shooter, a fantasy bow-and-arrow game, a Captain America shield game) can reuse the same hub without regenerating it.

  * **Repulsor Blast** — The repulsor blast fires a beam-style Iron Man projectile out of whichever gauntlet the player has equipped, when they press the trigger on that same side. Pressing the right trigger with only the left gauntlet equipped does nothing, and pressing the left trigger with only the right gauntlet equipped does nothing. This mechanic explicitly depends on the Shooting-Hub being created first, because it builds *on top of* the hub — it does not re-implement grab, equip, or trigger listening, since Shooting-Hub already sits on top of Grab and Equip. The Repulsor Blast's generated code therefore needs to:
    * **A.** Register a `weapon_profile_id` of `iron_man_repulsor` against the Shooting-Hub, so the hub knows to call into this code whenever a gauntlet with that profile receives a trigger press.
    * **B.** Match the trigger side against the gauntlet's equipped side, so the left-gauntlet profile only fires on left-trigger pulls and the right-gauntlet profile only fires on right-trigger pulls.
    * **C.** Implement the actual visual and gameplay behavior of the blast — the beam's spawn point at the palm of the gauntlet, the beam's direction aligned to the gauntlet mesh's forward axis, the canonical gold/blue-white VFX, any charge or cooldown timing, and whatever the blast does on impact.

In the **SceneSpec** stage the engine takes the BuildSpec, AssetManifest, and MechanicPlan together and composes one `SceneSpec` JSON per scene defined in the BuildSpec. For this Iron Man game that is a single SceneSpec for the New York scene. The scene composer (Claude Opus) is given all three upstream artifacts plus the live engine catalog and produces a deterministic entity / component layout that does four things:

* **It places the player spawn.** The composer picks a sensible point inside the New York environment (for example, at street level on a Manhattan block, eye height 1.7 m, facing down the block toward whatever the prompt described as "the action"). The player rig that gets spawned here is what the locomotion and snap-turn mechanics drive at runtime — there is no separate player-controller code, the rig is just an entity that those built-in mechanics bind to.

* **It places one entity per `AssetItem` from the AssetManifest**, each pointing at the right GLB and tagged in a way the rest of the engine can react to. For this game the composer emits:
  * A `manhattan_city` entity at position `[0, 0, 0]` with rotation identity, `physics.kind = "static"`, `physics.collision_shape = "mesh"` (so the player can actually walk on the sidewalks and collide with buildings), and tags `["environment"]`. The player spawn sits on top of this entity.
  * A `gauntlet_left` entity within arm's reach of the spawn (e.g. ~0.6 m in front of and slightly to the left of the player, at hand height), referencing the gauntlet GLB, with `physics.kind = "dynamic"`, an AABB or sphere collision shape, and tags `["interactable", "grabbable", "wearable", "weapon", "hand_left"]`.
  * A `gauntlet_right` entity symmetric to the left, tagged `["interactable", "grabbable", "wearable", "weapon", "hand_right"]`.

* **It wires every mechanic from the MechanicPlan onto the right entities** via `MechanicBinding` entries. This is the moment the planner's abstract classifications become concrete runtime wiring:
  * The player rig gets a `builtin.smooth_locomotion` binding and a `builtin.snap_turn` binding (no params beyond defaults — the engine handles joystick polling internally).
  * Each gauntlet entity gets a `builtin.grab` binding, so the engine's Grab mechanic recognizes them and makes them grabbable on a grip-squeeze.
  * Each gauntlet entity gets a `builtin.equip` binding carrying the exact parameters the MechanicPlan tuned for this game: `{ "slot": "forearm_left"` or `"forearm_right", "coverage_start": "fingertips", "coverage_end": "elbow", "pair_with": "gauntlet_right"` (or `"gauntlet_left"`) `}`. This is exactly the per-game tuning that made Equip a `builtin+config` instead of a plain `builtin` — the configuration travels as parameters on the binding, not as a new C++ file.
  * Each gauntlet entity also gets a `generated.shooting_hub` binding declaring it carries a weapon profile, plus a `generated.repulsor_blast` binding with params like `{ "side": "left"` or `"right", "weapon_profile_id": "iron_man_repulsor", "muzzle_anchor": "palm", "forward_axis": "z+" }`.

* **It places the lights and sky** for the scene. For daytime Manhattan that means one directional "sun" light angled across the block, a daylight sky color, and a moderate ambient intensity so the gauntlet's PBR materials read correctly under the sun-plus-shadow lighting.

In short, the SceneSpec is the bridge between the abstract MechanicPlan and the deterministic runtime. It turns sentences like "the gauntlet should be grabbable, equippable on the forearm, and fire repulsors on trigger" into concrete entity ids, transforms, mesh refs, tags, and mechanic bindings that the engine's scene loader can apply directly to the ECS world — and that the C++ code-generation stage can target by name.

In the **Code Generation** stage the orchestrator turns each `generate` entry in the MechanicPlan into a `CodeTask` and dispatches it to a worker. Because the Repulsor Blast depends on the Shooting-Hub, the orchestrator schedules them in dependency order: the Shooting-Hub task is launched first, and the Repulsor Blast task is held until Shooting-Hub finishes. Tasks that have no dependency between them, however, can be worked on by two workers in parallel, and as soon as Shooting-Hub's outputs land in the ledger the Repulsor-Blast worker is unblocked and begins.

* One worker is assigned to the **Shooting-Hub** task and follows a disciplined flow:
  * **A.** It reads the task metadata — name, summary, the `ptv::IMechanic` interface it must implement, its `depends_on` list, the assets it is linked to, and its target scene (New York).
  * **B.** It loads completed dependency outputs from the ledger. It sees that Shooting-Hub depends only on the built-in Grab and Equip mechanics, both of which are already part of the engine's public surface under `engine/runtime/include/ptv/api/`, so there is nothing to wait on.
  * **C.** It may use the web search tool to research the best way to design a generic shooting hub for a VR game — so the hub is a clean central abstraction that every shooting-style in-game mechanic (pistols, rifles, RPGs, laser blasters, repulsors, bow-and-arrow, etc.) can be built off of without each weapon re-implementing input handling.
  * **D.** It writes the C++ files needed to implement the hub at `engine/generated/mechanics/<project_id>/shooting_hub.cpp`. The file implements `ptv::IMechanic`, registers itself with `PTV_REGISTER_MECHANIC("shooting_hub", ShootingHub)`, listens for the correct trigger (left or right) only when the bound entity has the `weapon` tag and is currently being held or worn, and forwards the trigger event to whatever generated mechanic has registered a `weapon_profile_id` against the same entity.

* Another worker is assigned to the **Repulsor Blast** task and follows the same disciplined flow:
  * **A.** It reads the task metadata — name, summary, the `ptv::IMechanic` interface, its `depends_on` list (which contains `shooting_hub`), its linked assets (the left and right gauntlet GLBs), and its target scene (New York).
  * **B.** It loads completed dependency outputs from the ledger. Because Shooting-Hub is in its `depends_on` list, this worker waits until the Shooting-Hub worker has finished and its outputs — the `weapon_profile_id` registration API and the trigger callback signature — are recorded in the ledger. Once they are, the worker reads exactly how the hub exposes those hooks so the Repulsor Blast plugs into the real surface and is not a reimplementation of grip or attach.
  * **C.** It may use the web search tool to research Iron Man, what a repulsor blast is and looks like, how the blast is fired from the palm of the gauntlet, VR projectile patterns, and gauntlet-aligned VFX (color, glow, trail, impact sparks).
  * **D.** It writes the C++ files at `engine/generated/mechanics/<project_id>/repulsor_blast.cpp`. The file implements `ptv::IMechanic`, registers an `iron_man_repulsor` weapon profile against the Shooting-Hub, matches the trigger side to the gauntlet's equipped side (left trigger fires only when the left gauntlet is equipped, right trigger fires only when the right is), spawns a beam or fast projectile from the palm anchor of the gauntlet mesh oriented along the gauntlet's forward axis, applies the canonical gold/blue-white color and motion of the repulsor, and respects any cooldown or charge timing the design called for.

The same pattern scales to any future game: one Shooting-Hub, many generated weapon profiles (guns, repulsors, bows, magic wands, energy waves), without ever regenerating locomotion, snap turn, grab, or equip for each new prop. And once this build succeeds, the engine's promotion stage indexes `shooting_hub` and `repulsor_blast` into `engine/promoted/registry.json`. The next prompt — say, "I want a Captain America VR game where his shield is grabbable, throwable, and fires energy waves" — will see those mechanics in the catalog as `promoted.shooting_hub` and `promoted.repulsor_blast`, and the planner will be able to mark Shooting-Hub as `builtin` for that game and only `generate` the new energy-wave weapon profile on top. That is the engine-growth loop: every game built on the platform makes the next game cheaper, more reliable, and faster to plan.

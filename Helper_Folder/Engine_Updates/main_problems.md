      * **(Issue)** The pistol and rifle are not randomly picking a "bigger LOD file." Every LOD is forced to the same longest-axis length, target\_scale\_meters, when it loads. A coarser LOD looks huge only when its bounding box is wrong, and which LOD is on screen at startup is a race.What the engine does. In GltfMeshLoad.cpp, the loader measures the mesh's longest axis and scales it so that axis equals target\_scale\_meters. LOD0, LOD1, and LOD2 are all supposed to end up the same size. The renderer in Renderer.cpp then picks a level by distance and, until the wanted file has streamed in, draws whichever coarser level is already in memory. Why the size changes between launches. stage\_asset\_optimize.py turns on \--sloppy for every static mesh from LOD1 downward. Sloppy simplification is allowed to invent vertex positions. That changes the bounding box. The loader still scales that broken box to target\_scale\_meters, so the gun body itself comes out much larger or much smaller than LOD0. The spikes under the guns in your second screenshot are those invented vertices. On Quest the LOD files load on a background thread, nearest first. At the weapon rack you are close, so the game wants LOD0, but it will draw LOD2 or LOD3 if those finish first. Whether LOD0 wins before you look is timing and memory, and the pistol and rifle stream separately. That is why one launch can show a huge pistol, the next a huge rifle, and the next both, with no change to the scene. LOD0 itself is not sloppy, so once it replaces the fallback the size should snap back. If a session stays huge the whole time, LOD0 failed to load and the gun stayed on a sloppy level.  
      * **(Solution)** Turn off sloppy simplification for these guns, rebuild their LOD files, and rebuild the APK. The files already in the project are the broken ones.In apps/orchestrator/ptv\_orchestrator/pipeline/stage\_asset\_optimize.py, LOD1 and below are built with \--sloppy. That flag lets the simplifier move vertices to hit a triangle budget. The moved vertices change the gun's bounding box. At load time, GltfMeshLoad.cpp then stretches whatever box it measured until the longest side equals target\_scale\_meters. A bad box becomes a giant gun. The detailed file, LOD0, is not built with \--sloppy, which is why it looks the right size when it wins the load race. Stop passing \--sloppy for static meshes (the same rule already exists for rigged characters). Then regenerate range\_pistol and range\_rifle LOD1–LOD3 from the original GLB, and package a new Quest APK. Until those files are replaced, the headset will keep loading the broken versions. A second safeguard, if you want sizes to be impossible to disagree: scale every LOD using the original mesh's longest side, not each LOD file's own box. Removing \--sloppy and regenerating is enough to stop the random giant guns.
